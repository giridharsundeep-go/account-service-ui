INTERNAL PLAYBOOK

AWS development deployment steps

Start with one UI and one backend
  1. 01

    Confirm the repository contract

    For each of the 32 repos, record its default branch, owner, build command, container port, startup command, health path, environment variables, and dependencies. Keep API contracts in OpenAPI. The repository cards below show known local ports; fields marked “Confirm from repo” still need source verification.

  2. 02

    Set up the AWS development boundary

    Choose one AWS region and a non-production account, set a budget alert, and create a VPC with public ingress and private application subnets across at least two Availability Zones. Keep EKS worker nodes and MySQL data off public subnets.

  3. 03

    Create EKS and image repositories

    Create an Amazon EKS cluster with managed EC2 nodes for the development workloads. Create one Amazon ECR repository per deployable app. Use Amazon RDS for shared MySQL data; install the EBS CSI driver only for workloads that need Kubernetes persistent volumes.

  4. 04

    Connect GitHub Actions without long-lived AWS keys

    Configure GitHub OIDC federation to assume a narrowly scoped AWS deployment role. On a protected branch, build the repo’s image, tag it with the commit SHA, scan it, push it to ECR, then update the Kubernetes release.

  5. 05

    Deploy into the development namespace

    Use a Helm chart or Kubernetes manifests per app. Define a Deployment, ClusterIP Service, readiness and liveness probes, resource requests and limits, and a ConfigMap for non-secret settings. Use separate namespaces for platform components and app workloads.

  6. 06

    Connect database-backed services to private RDS

    Use the EKS Spring profile for each MySQL-backed service. Keep RDS private in the same VPC, allow inbound port 3306 only from the EKS workload security group, and source DB_USERNAME and DB_PASSWORD from a runtime secret. Use a separate schema per service rather than the MySQL system schema.

  7. 07

    Expose only approved entry points

    Keep backend Kubernetes Services private. Route public APIs through the central API Gateway using a private VPC Link integration to an internal load balancer. Expose UI hosts through an AWS Application Load Balancer with HTTPS and an approved host rule.

  8. 08

    Attach the domain and verify the release

    Create the Route 53 hosted zone and ACM certificates for developers.greatley-poshley.com and the API domain. Route the developer hostname to this app’s /developers path, or configure an ingress redirect from /. Cloudflare can remain the registrar while its nameservers point to Route 53; transfer registration only if you want registrar management in AWS too. Verify login, health checks, API authorization, logs, and rollback before inviting developers.

RDS connection profile

The database-backed services use schemas chatly, professy, professy_email, professy_notification, greatley_identity, greatley_calendar, greatley_instru, and greatley_mail. Activate SPRING_PROFILES_ACTIVE=eks, create these schemas before starting the Pods, and set DB credentials from Secrets Manager through a Kubernetes secret integration. Download the schema bootstrap SQL.

The profile requires encrypted TLS connections without a CA file. Certificate identity verification is a separate setting and requires a trusted RDS CA in the Java trust store.

API CATALOG AND CONTROL PLANE

One central API Gateway

AWS API Gateway REST API

Use one logical gateway for developer-facing APIs, with a route registry that assigns every route to a service owner. Keep backend Services private inside EKS.

Client→API Gateway
authorizers · quotas · throttles · WAF→VPC Link v2→Internal ALB→EKS API Service
01

Organize APIs and routes

Use one gateway with route prefixes grouped by product, such as /auth, /accounts, /chat, /documents, and /calendar. Each entry needs an OpenAPI spec, owner, backend Service, data classification, stage, and deprecation date.

02

Apply usage plans

Create development and production plans per consumer. Set per-method rate and burst targets, plus quotas where useful. Use separate keys per app, environment, and integration so a leaked key can be revoked without affecting other clients.

03

Keep keys out of code

Use API Gateway generated key values. Store issuance metadata—owner, consumer, environment, plan, creation date, rotation date, and status—in the internal registry. Deliver values through an approved secret channel; never commit them or embed them in browser code.

04

Protect identity separately

API keys identify usage-plan consumers and support metering. They do not authenticate a user or grant authorization. Require the shared identity provider/JWT or a Lambda authorizer, and use IAM authorization for trusted service-to-service calls.

Gateway policy

Usage-plan throttles and quotas are best-effort targets, not hard security or cost limits. Pair them with AWS WAF rules, authorization, CloudWatch alarms, and AWS Budgets.

INTERNAL SECURITY BASELINE

Access, keys, and operations

Developer portal access

Keep the portal authenticated. Enforce access at the AWS ingress or identity layer as well as in the Angular route; a browser-side route guard is not an access-control boundary. Use the workspace identity provider or an ALB OIDC/Cognito rule and limit access to developer groups.

Credential lifecycle

Issue scoped, named keys per consumer and environment. Record owner and expiry, rotate by overlap-and-revoke, revoke immediately on suspected exposure, and review unused keys regularly. Never put secrets in GitHub, container images, frontend bundles, or logs.

Network and data

Use TLS for every public endpoint. Keep MySQL and internal APIs in private subnets, allow only required security-group paths, and use Kubernetes Secrets backed by AWS Secrets Manager or a secrets CSI integration for runtime credentials.

Audit and recovery

Enable API Gateway access logs, EKS control-plane logs, CloudTrail, and application metrics. Alert on 4xx/5xx spikes, throttling, unhealthy Pods, and database storage. Maintain an image rollback path and a tested database restore procedure.
